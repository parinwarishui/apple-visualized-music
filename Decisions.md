# Changelog and decisions

All notable changes to Apple Visualized Music, newest first, in the [Keep a Changelog](https://keepachangelog.com) style. Each entry says what changed and why, so a removed feature isn't re-added by accident.

Dates are the days the work was done. Everything from 2026-10-15 happened in one working session, so it's grouped by type of change, not by hour.

## avm-reverbdsp branch - 2026-10-22

Separate branch (`git worktree .worktree-reverbdsp`), not merged to main. Goal: replace both the stock `AVAudioUnitReverb` (reported "murky") and the unmerged `avm-supermassive` branch's hosted-plugin approach with a real, from-scratch reverb — by porting the convolution engine already built, tuned and shipped in `reverb-room`, a sibling project co-developed with this one that went further on exactly this problem.

### Why porting beat both earlier directions
- **Apple's stock `AVAudioUnitReverb`** has no reverb-return EQ, so the tail's own low-mid/high-mid energy stacks on top of the song's — the likely cause of "murky."
- **`avm-supermassive`** (hosting a user-installed Valhalla Supermassive) sidesteps the licensing question but trades it for a real dependency (the user must have Supermassive installed), a security trade-off (`com.apple.security.cs.disable-library-validation` to load third-party code under the hardened runtime), an in-process AUv2 crash risk, and nine parameter fractions + five Mode mappings that are explicitly "not yet confirmed by ear" guesses from Valhalla's marketing copy, not measurements.
- **`reverb-room`'s `ReverbDSP` module** has none of that: no plugin, no install dependency, no library-validation entitlement. It's pure Swift/C, already built, and ships with its own offline self-check (`./build.sh check` in `reverb-room`) that verifies the convolution math, the limiter and BS.1770 conformance without needing to listen — the opposite of this app's recurring "not yet confirmed by ear" problem.

### What was ported, verbatim
- `Sources/ReverbDSP/{Biquad,RealFFT,Convolver,ImpulseResponse,Loudness,ReverbProcessor,Atomics}.swift` and `Sources/RRAtomics/{RRAtomics.c,include/RRAtomics.h}`, copied unchanged from `reverb-room`. The module has zero dependency on anything reverb-room-app-specific (no `AppTapPipeline`, no `ReverbSettings`) — it only needs `Foundation`/`Accelerate` and its own atomics target, so it dropped into AVM's `Package.swift` as two new targets (`RRAtomics`, `ReverbDSP`) with no other change.
- **Not ported (out of scope for this pass):** `PitchShifter`/`RRStretch` (pitch shifting — AVM doesn't have a pitch control) and `SongAnalyzer` ("Adapt to the song" — AVM already does its own band/hit analysis for the tank visualizer, via a different mechanism; worth revisiting later as a shared analysis path rather than a second one).

### How it's wired into AVM, differently from reverb-room
- **reverb-room has no `AVAudioEngine` graph at all** — it processes raw deinterleaved tap buffers directly (tap → pitch shifter → `ReverbProcessor` → output). AVM still uses `AVAudioEngine` in manual rendering mode for the EQ and Filter (Apple's own `AVAudioUnitEQ`/`AVAudioUnitEffect` nodes), so `ReverbProcessor` could not be just another graph node without writing a full custom `AUAudioUnit` subclass. Instead, exactly like the (abandoned) `avm-freeverb` worktree's approach but with the ordering bug that branch flagged in its own header comment fixed: `Renderer.process` calls `reverb.process(left:right:frames:)` directly on the engine's already-rendered `wetL`/`wetR` buffers, in place, *before* the existing hard clip — so reverb is still the last stage before output, as the signal-flow diagram at the top of `AudioPipeline.swift` has always said, not after the limiter the way `avm-freeverb` had it.
- **The engine's own Apple peak-limiter node is gone.** `ReverbProcessor` carries its own lookahead true-peak limiter as its last internal stage (4× oversampled, program-dependent release) — strictly better than the stock `AVAudioUnitEffect`/`kAudioUnitSubType_PeakLimiter` it replaces, and running both would be redundant. The hard clip in `Renderer.write` stays, as the final safety net either way.
- **AVM's five "Space" presets became three numbers each** (`AVMReverbSpace.shape: ReverbShape` — decay/RT60, pre-delay, tone) instead of an `AVAudioUnitReverbPreset` or a plugin Mode. Hall and Cathedral reuse reverb-room's own "Concert Hall" and "Cathedral" room numbers directly (already tuned there); Room, Chamber and Plate are new, picked to fit what those names mean on AVM's reverb specifically. **Not yet confirmed by ear** — same standing caveat as the rest of this file.
- **On/off is now "turn the mix to 0," not an AU bypass.** `ReverbProcessor` has no bypass concept (reverb-room's own UI has no on/off switch at all — it's always running, amount 0...1). To keep AVM's existing per-effect switch, `TapPipeline.setReverbEnabled` now just drives `ReverbProcessor.setMix(0)` instead of toggling `kAudioUnitProperty_BypassEffect`. Trade-off accepted: the convolution engine and limiter now always run once a session starts (reverb-room measures about 2% of one core for its longest room, so this is not a CPU concern), and there's a small, constant, latency cost (~26 ms at 48 kHz per reverb-room's own measurement: one 1024-sample block plus 5 ms of limiter lookahead) whether or not the module is switched on, instead of zero added latency while off. Not yet confirmed by ear whether that's audible against this app's existing tap/aggregate-device latency.
- **`TapPipeline.collectGarbage()`**, called from `AVMController.checkHealth()`'s existing 0.5 s watchdog tick, frees the impulse response the audio thread has finished with after a preset change — the same place and cadence reverb-room's own `Model.tick()` calls it.

### Still open
- **Not yet confirmed by ear**, same caveat as the avm-supermassive branch and most of this file: the Room/Chamber/Plate shape numbers, and whether the always-on ~26 ms latency is noticeable.
- **Consolidated onto this branch.** This was first built in its own `.worktree-reverbdsp` worktree; the Supermassive-hosting code this branch had already added (`SupermassiveReverb.swift`, `SupermassiveControls.swift`, the app-identity rebrand) is removed here in favor of this engine, and the `avm-supermassive`/`avm-freeverb` worktrees are removed — their branches still exist if either is worth revisiting.
- **SongAnalyzer ("Adapt to the song") was deliberately not ported this pass.** AVM's `BandSplitter`/`HitDetector` already do real-time band analysis for the tank visualizer; feeding a reverb auto-tuner from the same source instead of reverb-room's separate analyzer is a reasonable next step, not done here.


## avm-supermassive branch - 2026-10-22

Separate branch, not merged to main. Goal: a noticeably better-sounding reverb than Apple's AUReverb2, after the user reported the live-effects output sounding "murky" and asked for a plugin swap.

### Dead ends ruled out first
- **Logic/GarageBand's ChromaVerb and SilverVerb are not loadable at all, by anyone.** They're compiled into Logic Pro/MainStage/GarageBand, not registered with the system's Audio Unit manager, so no other host — not AVM, not even other DAWs like Ableton or Studio One — can see them. Installing GarageBand would not have exposed them. Confirmed against an Apple discussion thread and a Logic-users-group thread; the only Apple reverb that *is* a real system-wide AU besides the one already in use (AUReverb2) is AUMatrixReverb, an older algorithm generally considered more metallic, not less — no free upgrade sitting in Apple's own toolbox.
- **Bundling a free third-party plugin (Valhalla Supermassive, TAL-Reverb-4) inside AVM's own app bundle isn't available.** Valhalla's terms: "No license is granted to redistribute the software as part of another software program, including video games, DAWs, etc." TAL's terms require written consent to distribute "this product," with no carve-out for the free ones. Even technically, both ship as classic AUv2 `.component` installers, not AUv3 app extensions — only an AUv3 can be embedded inside another app's own bundle with zero separate install; an AUv2 always needs its own system-wide install step.
- **A hand-written reverb algorithm (Freeverb) was the fallback plan** if hosting the user's own installed plugin turned out not to work, since it's the only path with zero licensing risk and no missing-dependency story. Not needed: hosting what the user already has installed sidesteps the licensing problem entirely, since AVM distributes no third-party code at all.

### What this branch actually does
- **Hosts whatever the user has installed, rather than bundling anything.** `SupermassiveReverb.locate()` searches installed Audio Units by name ("Supermassive") and loads it with `AVAudioUnit.instantiate`. If it's not installed, AVM falls back to the stock reverb, unchanged — the base AVM app's behavior is the floor, not a regression.
- **Needs `com.apple.security.cs.disable-library-validation`** (new in `AVM.entitlements`), because the hardened runtime otherwise refuses to load any code not signed by AVM's own Team ID — confirmed against an Apple DTS-backed forum thread on sandboxed third-party-plugin hosting, and a JUCE host developer's write-up of the same fix (also: `--options runtime,library` on the codesign call silently re-enables validation even with the entitlement present, which tripped up that developer — `build.sh` here only ever passes `runtime`). This is a deliberate, scoped trade-off against the hardened-runtime protection the base app chose; it's why this is its own branch/app (`AVM SuperMassive`, separate bundle ID) rather than a change to base AVM.
- **No hardcoded parameter addresses.** Valhalla doesn't publish Supermassive's internal parameter IDs or ranges, and this device's shell can't run `auval -v` against the real plugin to find them. Every control is found by matching its `AUParameterTree` display name at runtime (e.g. "mix", "mode", "width") and every numeric value is set as a 0...1 fraction of that parameter's own live min...max, not an absolute number. A parameter that isn't found is logged once and left alone rather than crashing or silently no-op'ing the whole preset.
- **In-process, not out-of-process.** Didn't restrict this to AUv3 (which would run the plugin isolated over XPC); AUv2 plugins load in-process, so a Supermassive crash takes AVM down with it, same risk as any plugin host. Accepted for now since it's the only way to know whether Supermassive ships AUv2, AUv3, or both until this is actually built and run.
- **Five preset → Mode mappings and nine parameter fractions are a first pass**, chosen from Valhalla's own written descriptions of its eight Modes (Gemini, Hydra, Centaurus, Sagittarius, Great Annihilator, Andromeda, Lyra, Capricorn), not measured by ear or against the real plugin — this device's shell has no audio output. **Not yet confirmed by ear**, matching this project's own standing caveat about everything else in the effects chain.
- **App identity only, not the executable or Package.swift target.** Changed `APP_DISPLAY_NAME`, `BUNDLE_ID`, and the matching `Info.plist` keys to "AVM SuperMassive" / `com.yourname.avm-supermassive`, so it installs and keeps settings separately from a base AVM build. Left `EXECUTABLE_NAME`/`CFBundleExecutable` as `AppleVisualizedMusic` and didn't touch `Package.swift` or `Tests/` — lower risk, and invisible to the user either way.

### Fixed (first real run, same day)
- **Mix was pinned near 100% wet at every slider position, including 1%.** `setMix` used `setExact` -- AVM's raw 0...100 slider value clamped straight into Supermassive's own Mix parameter. If that parameter's range is normalized (0.0...1.0, a common AU convention, display formatted as a %), any UI value >= 1 clamps to the parameter's maximum: "1%" was actually sending 100% wet every single time, which is exactly what "way too intense, can't hear music even at 1%" sounds like. Fixed by scaling Mix as a fraction of the parameter's own live range, like every other control here, instead of assuming its units match the UI's. The now-dead `setExact` helper was removed.
- **Preset fractions pulled back.** Warp/Feedback/Density were tuned (by description, not by ear) up to 0.7-0.9 of each parameter's range. Even once Mix is correctly scaled, Supermassive's own character leans toward huge/dense at moderate settings, so all five presets were brought down (Cathedral's ceiling dropped from ~0.8 to ~0.55) until there's an actual listening test to tune against.
- **Added one-time logging of the plugin's real interface** (`SupermassiveReverb.logDiscoveredInterface`, called right after a successful load): every `AUParameterTree` display name, and every factory preset name Supermassive itself reports. Neither was available from Valhalla's public docs (checked; no reliable source for the exact factory preset list), so this is the only way to get real data instead of another guess — check `./build.sh debug` for the "Supermassive parameters:" and "Supermassive factory presets:" lines. The factory preset list in particular is likely a better source for a natural-sounding default than this file's hand-picked fractions, since Valhalla tuned those by ear and this file hasn't; worth switching the five "Space" presets to select one of Supermassive's own factory presets by name once that list is known, rather than driving Mode + 9 raw parameters from here.

### Added (same day, second request)
- **A generic "full control" rack** (`SupermassiveControls.swift`) showing every parameter Supermassive itself reports — not a fixed list AVM assumes exists, but whatever `tree.allParameters` actually returns, so it's automatically right regardless of what the real display names turn out to be. Discrete/indexed parameters (Mode) get a `Picker`; everything continuous gets a custom circular `KnobControl`, since SwiftUI has no built-in radial drag control (same reason `EQBandSlider` elsewhere in this app rotates a horizontal `Slider`, but a rotated linear slider doesn't read as a knob, so this one's drawn from scratch: a trimmed `Circle` arc plus a rotating pointer rectangle, dragged vertically). Sits in a collapsed `DisclosureGroup` under the five Space presets, which stay the default. **Not seen rendered** — written without a SwiftUI preview or a real device; knob size, drag sensitivity (120 px of vertical travel = full range) and grid layout are first guesses.
- Binds directly to live `AUParameter` objects from the main thread, skipping `TapPipeline`'s work queue — `AUParameter.value` is documented thread-safe for live automation, unlike the raw `AudioUnitSetProperty`/`AudioUnitSetParameter` calls the stock Apple units use elsewhere in this file, which is why those ones *do* go through the work queue.

### Still open
- **Still not confirmed by ear past the Mix bug.** The fraction pull-back above is reasoning from "Supermassive tends to be big," not a listening test.
- **Whether Supermassive is AUv2 or AUv3** is unconfirmed, which decides the crash-isolation question raised when this branch was created.
- **The exact AUParameterTree display-name strings and factory preset names** are now logged at load time instead of guessed, but that log hasn't been read yet.

## [0.1] - 2026-10-20

### Added
- **Fish style** (user request). A school of 12 minimal fish (oval body, forked beating tail, eye), 4 per band in that band's cover colour, in varied sizes (bass biggest, treble smallest). A fish's colour brightens with its band (the song's loudness, or kicks and hi-hats) and its size never changes, as asked. Movement is unpredictable but calculated: per fish, two slow waves per axis with periods in an irrational ratio (never repeating), on a clock that speeds up and slows down (darting), with vertical waves about twice as slow and the tilt capped at 30° so fish cruise rather than climb (first render had fish pointing straight up). Seaweed (11 swaying strands, swaying further when the song is loud) and coral (5 branching fans; first drawn as mounds of circles, which read as blobs) along the bottom; bubbles rise, brighter on hi-hats. All pure functions of time, unit-tested, and checked by rendering frames offscreen.
- **Fish flare on their band, intensely** (user: the colour change should be as quick and obvious as the other styles' size pulses). It already used the same fast pulse; it was just too faint (tone 0.2–0.85 on the blob colour scale). Now a fish rests at 45% brightness and on a hit flares through its cover colour to 45% towards white, with a glow halo up to 1.5× its length around it. Song fish glow with loudness above the usual level. A first try at 60% towards white turned flaring fish nearly white, losing which band they were, so it was pulled back. Checked by rendering a quiet frame, a kick and a hi-hat in a loud passage.
- **No glow halo; tails joined to the body** (user request). The halo around flaring fish is gone; only the fish's own colour changes. Body and tail were two fills that overlapped, and screen blending showed the overlap as a brighter patch; now they're one shape (`Path.union`) filled once, the tail tucked just inside the body so there's no gap. Checked by rendering at full sharpness.

### Fixed
- **The playhead ran ahead of the song, then snapped back, over and over** (user report). Measured first: Music's own position is steady (counting forward from one reading stays within 0.07 s for 20 s), and inside the app the clock matched Music to 0.01 s at every check, so neither the counting nor the audio pipeline (no growing buffer) was at fault. The loop matches Music reporting "playing" while loading or buffering a song with its position standing still: the clock counted on, the 5 s re-read pulled it back, and again. Now `PlaybackClock` holds still when two readings barely move (stalled), and the playhead is re-read every 0.5 s while stalled and for 4 s after a song starts, resumes or is seeked, otherwise every 2 s (was 5 s). A new song also starts its clock at 0 instead of carrying the old song's position until the first read. Unit-tested; a live buffering stall wasn't reproduced, since that meant seeking the user's music mid-listen.

### Added
- **Apple Visualized Music (AVM) set up as its own project and repository.** Everything below is the work it starts from. The app is "Apple Visualized Music"; the binary and Swift module are `AppleVisualizedMusic`; the bundle ID is `com.yourname.apple-visualized-music`; everything internal (source folder, types, C meter functions `avm_meter_*`, queue labels, log prefix `[AVM]`, entitlements file, `AVM Dev` certificate) uses the `AVM` prefix. Version reset to 0.1. A new bundle ID means new macOS permissions (system audio recording, Automation for Music) and fresh saved settings.

## 2026-10-19

### Changed
- **The tank fills the window** (user request). It used to be a 400 pt pane on the left; now it's edge to edge with no rim, and the window can be resized or made full screen (minimum 976 × 800) with the tank growing to fit. The player, effects and visualizer settings moved into a 560 pt sidebar on the right that slides in and out from a toolbar button (⌃⌘S, saved as `sidebarShown`). The sidebar keeps a fixed width so labels still never wrap, which was why the window used to be fixed. The visualizer settings sit pinned at the sidebar's bottom; the rest scrolls if the window is short.
- **Floating panel and a full-screen player** (user request, same day). The sidebar is now a detached rounded card (frosted at first, now a translucent fill: see Performance; with the cover wash, border, shadow) inset from the window edges, hidden and shown by a glass chevron tab beside it instead of a toolbar button. With it hidden, the window shows Music's full-screen look in the bottom-left corner: the cover with the song name large and the artist small beside it. The panel and the player take turns (panel out, then the player fades up into place; player fades down and out, then the panel slides in) instead of animating at once. This also fixed a stray horizontal line across the middle of the old sidebar: a `Divider` meant for its left edge sat in an overlay, not an `HStack`, so it drew horizontally.
- **Blobs renamed to Bokeh**: that's what soft, blurred discs of light are called in photography. Saved `tankMode` values of `blobs` fall back to it.
- **Three times as many bokeh discs** (user request): 18 instead of 6. `TankBlobs.bokehLayout` draws each blob path three times, the copies shifted 23.7 s and 47.3 s along it and mirrored left–right or top–bottom, so they look independent rather than trailing each other. The other styles keep the six blobs.
- **Smaller, crisper bokeh** (user: the bokeh was blurrier than the other styles at the same Focus, and the circles too big). Each disc is now a quarter of its blob's radius (`TankScenes.bokehSize`), is solid for its inner half before fading (`bokehSolid`; sharper focus widens that), and gets 0.4 of the Focus blur instead of the full amount, between rain (0.28) and drops (0.6).
- **Bigger water drops**: each drop is 0.52 of its blob's radius, up from 0.36.

### Performance
Measured on the release build in a full-size window (1512 × 876 pt, Retina), with Music playing and the effects off. GPU is the system's "Device Utilization" (3% with the app closed). These numbers swing a few points run to run.

| | Before | After |
| --- | --- | --- |
| GPU, panel shown | 22–41% | 15–18% |
| GPU, panel hidden | 14–16% | 12–17% |
| App CPU | 8–11% | 9–11% |
| Memory footprint | 214–340 MB | 154–201 MB |
| Main thread blocked per Music read | 40–80 ms, every 5 s | none |

- **Music scripting moved off the main thread** (`MusicEvents.swift`). Each `NSAppleScript` blocked the window 40–80 ms (timed in-process: track and cover about 64 ms, playback about 47 ms), so the visualizer skipped two frames on every 5 s playhead resync, and a button press froze it for about 90 ms. `NSAppleScript` may only run on the main thread, so the scripts became raw Apple Events, sent on a serial background queue; the cover is decoded there too. Checked against AppleScript's answers, and setting shuffle and repeat was checked by flipping and restoring them. Play/pause, next and back weren't tested live, so as not to interrupt playback.
- **The tank renders at a lower resolution when blurred** (`TankView.renderScale`). Blur hides pixels smaller than itself, so with a blur of 3 pt or more the tank is drawn at 1× instead of Retina 2×, and at 0.5× from 12 pt up; only a nearly sharp tank uses full resolution. It's drawn into a smaller `Canvas` in the same coordinates (`scaleBy`), in a `drawingGroup`, and scaled up. Blur radii scale with the drawing (checked offscreen: the same 24 pt edge at both sizes), so it looks the same. Its offscreen buffers (IOSurface) fell from 47 MB to 8–16 MB.
- **The panel is a plain translucent fill, not frosted glass.** The blurring material re-blurred the moving tank behind it on every frame, adding about 12% GPU whenever the panel showed; a 94% opaque window-colour fill with the cover wash costs about a third of that. Its shadow is now cast by a plain shape, so it isn't redrawn whenever the playhead or tint changes.
- **Fixed: the player view now fades out** when the panel comes back. A `ZStack` put the leaving view behind the tank, so its fade-out was never seen; `zIndex(1)` keeps it on top.
- Tried and dropped: setting `displayScale` on the `Canvas` doesn't change how it's rasterised, and saved nothing.
- Not measured: the audio pipeline with the effects on (turning them on would have changed what was playing mid-listen). The remaining memory is mostly the system's own graphics buffers (about 118 MB) plus about 20 MB of live heap.

### Removed
- **Shapes and Comet styles** (user request). A saved choice of either falls back to Bokeh.

## 2026-10-16

### Changed
- **Focus works along the whole slider, for every style** (user: some styles stopped being blurry before the slider was even halfway). The blur used to fall to zero at 0.35 and only the blobs changed beyond that. Now the blur shrinks steadily from 0 to 1 (`TankFocus.blurRadius`, zero only at 1), and blobs also tighten their soft edge in the sharp half (core from 0.5). The default moved from 0.35 to the middle, 0.5. Each style gets its own blur strength (`TankMode.blurAmount`: blobs 1, drops 0.6, comet 0.5, shapes and rain 0.28), because a blur that suits big soft blobs wipes out thin lines; checked by rendering Rain at 20%, 50% and 80%.
- **Bigger raindrops** (enlarged twice at the user's request). Ripples spread to 0.30–0.92 of the tank scale (first 0.10–0.32, then 0.18–0.56), with four rings instead of three, thicker lines (1.5–6 pt) and a bigger splash.

### Added
- **Visualizer styles**, picked from a **Style** menu above Focus and Speed (saved as `tankMode`). All share the water, the three band colours and the hit/loudness reactions; each is drawn into the same blurred, screen-blended layer, so Focus works for all of them.
  - **Blobs**: the original.
  - **Shapes**: bass as a circle and a square, treble as two triangles, the song as two wavy strings across the tank (wavier when loud, a fine shiver on hi-hats). They ride the blobs' paths and turn slowly; outlines with a soft glow and a faint fill.
  - **Water drops**: one drop per blob, each a core plus four lobes orbiting at different rates and a satellite droplet that drifts off, pinches away and rejoins every 9 s. Each band's drops are blurred together and cut at half opacity (the "metaball" technique: `blur` then `alphaThreshold`), so they merge and split like liquid with surface tension. Kicks throw the lobes outward. (A soft white glint on each drop was tried and removed on 2026-10-16: it read as a stray oval.)
  - **Comet**: one comet on a looping path with a 2 s flickering tail, white-hot at the head, fiery near it and fading through the cover's colours, throwing sparks. Each kick softly lights up the tank around the head and swells it; hi-hats brighten the sparks; a loud song lengthens the tail.
  - **Rain**: drops land on the water and spread rings. The steady rain follows the song's loudness (0.8 to 5.8 drops a second); each kick lands a big drop and each hi-hat a small one, in their band's colour. Ripples are the only stateful part (they start on hits), kept in `RainField` in the model; everything else is a pure function of time.
  Sparks, wobbles and drop positions use a hash of an index rather than a live random generator, so a frame always looks the same when redrawn. Checked by rendering each style to an image; motion code is unit-tested (80 tests in all).

### Changed
- **Calmer drum hits** (user: the size pops were too glaring and fast). A full hit now swells a blob by 15% (bass) / 10% (treble) instead of 35% / 25%; each pulse eases in over about 60 ms (kicks) / 30 ms (hats) instead of jumping in one frame, held at its height for that long before fading (0.22 s kicks, 0.08 s hats); and a hit lifts the blob to tone 0.85 (`TankTone.hitPeakTone`) instead of the full white flash. Every kick still gets its own visible pulse that mostly fades before the next one (simulated at 120 BPM and with 16th-note hi-hats, and unit-tested). Confirmed by the user on real music before this change that hits now register, but only with the effects on (the tank has no audio reading otherwise).

## 2026-10-15

### Added
- **Hit detection for the bass and treble blobs** (user: they didn't react clearly enough to drums and treble). Following each band's loudness wasn't enough: a sustained bass line or a busy cymbal pattern kept the band near its own average, so hits blurred together. Now `HitDetector` fires a pulse when a band jumps more than 2.5 dB above its level over the last fraction of a second (0.35 s for bass, 0.2 s for treble), at 50–100% strength depending on the size of the jump, then lets it die away (0.22 s for kicks, 0.09 s for hats, so 16th-note hi-hats still separate). A short hold (0.12 s / 0.06 s) stops one hit firing twice. Between hits, bass and treble blobs rest dim (tone 0.2–0.5 by band level); a hit lifts them to full brightness with the white flash, and swells them up to 35% (bass) or 25% (treble) on top of the loudness size. The song blobs are unchanged, so they still show the slow verse/chorus swell. Done on the 30 fps UI side, reading the band peaks the audio thread already holds, so no extra audio-thread work. Unit-tested with synthetic kick and hi-hat patterns; not yet checked by eye on real music.
- **Three cover colours, one per band.** The palette picker now returns the cover's **3** most evident colours (k-means into 6 clusters instead of 5, each pick clearly different from the others). Covers with fewer distinct colours are filled out with a darker or lighter shade of their own, whichever differs most. Each band gets one colour for both its blobs (bass, song, treble) instead of every band using both colours, so you can tell at a glance which part of the music is moving. Which colour goes to which band is shuffled on every song change, as asked ("no deterministic order"); the picker itself stays deterministic so it can be tested. The water is now the darkest of the three. Measured: about 0.16 ms per cover in the release build, once per song change.
- **Window tint.** The window background is a light wash (16% at the top, fading to 6% at the bottom) that drifts through the cover's three colours, one full cycle every 45 s, easing so it lingers on each. Dark colours are lifted first so the wash tints the window rather than greying it, which keeps the native light look. For efficiency the tint is updated 5 times a second, not 30, and lives in its own small view (`AmbientBackground`), so only the background redraws; it pauses with the tank when the window is hidden. A fifth of a second never moves the colour visibly (unit-tested).
- **Blob speed slider** (tortoise to hare, 0.2× to 3×, default 1×, saved as `tankSpeed`) under the Focus slider. It scales how fast the tank's clock advances rather than the paths themselves, so changing it never makes the blobs jump. Paused Music still slows them to 35% of the chosen speed. Right-click for **Reset Speed**.
- **Tank focus slider** under the tank (user asked to control how blurry the blobs are). One 0–1 `focus` value (`TankFocus`, persisted as `tankFocus`, default 0.35 = the previous look). Below the default the blob layer gets a real Gaussian blur, up to 12% of the tank scale (about 33 pt). Above it, each blob's radial gradient keeps a solid core of up to 90% of its radius, so blobs become crisp discs; a thin soft rim stays so edges don't alias. Blur and sharpness are split this way so one slider covers both, and the middle is exactly the old look. The blobs are drawn into one `drawLayer` so the blur is a single filter pass, not one per blob; the layer is screen-blended onto the water like the blobs were. Right-click the slider for **Reset Focus**. The mapping is unit-tested (52 tests).
- **Drum- and treble-reactive blobs.** Each pair of blobs follows its own part of the music: the two large ones the **bass** (low-pass at 150 Hz: kick drums, bass lines), the two small ones the **treble** (high-pass at 5 kHz: hi-hats, cymbals), the two medium ones the overall loudness as before. Two second-order filters on the audio thread instead of an FFT: a few operations per sample, real-time safe, and two bands were all that was asked for. Band levels are stored as fast-decaying peaks so hits between UI reads aren't missed, and they use a punchier response (`.hits`: 2.5 s average, ±6 dB, 30 ms rise, 0.25 s fall). Checked live on a real track: bass and treble blobs moved independently (bass dark during a bass drop-out while a treble burst lit the treble blobs fully). Filters, the hit response and the blob assignment are unit-tested (49 tests).
- **Now Playing mini player** at the top of the right column, modelled on Music's MiniPlayer: cover, "Now Playing", "Artist – Track", a draggable playhead with elapsed/remaining time, and shuffle, previous, play/pause, next and repeat. Uses the existing Automation approval (the permission text now says the app also sends player commands). The playhead is counted locally between readings (`PlaybackClock`, unit-tested) and re-read from Music every 5 s while playing and after every command, so it moves smoothly without scripting Music each tick, and still picks up changes made in Music. Title and artist come from Music's notification, so they show even without Automation. Previous is Music's `back track` (restart, then go back), and repeat cycles off → all → one, like Music. Window grew to 976 × 800 to fit it.
- **Album-art tank.** A 400 pt wide pane down the left of the main window (first built as a 140 pt strip across the top, then enlarged): six soft blobs in the current Music song's two most evident cover colours, drifting over dark water, lighter in the song's loud passages and darker in its quiet ones (loudness judged against the song's own 12 s average, ±8 dB). Rests at mid-tone with the effects off; dims and slows when Music is paused; cross-fades on track changes. Every decision and its reason is in [docs/album-tank-plan.md](docs/album-tank-plan.md); key ones: artwork by scripting Music (one-time Automation prompt raised off the main thread, never launching Music), iTunes Search fallback for songs with no artwork, `Canvas` redrawn by a 30 fps `Timer` (not `TimelineView`, which failed before) that idles while the window is hidden, and loudness only while the effects run (no second capture).
- **RMS metering.** `AVMAtomics` now keeps a short (about 50 ms) exponential average of the tapped audio's mean square; `Meter.rms` reads it. Needed by the tank; computed in the loop that already found the peak.
- **Unit tests** (`./test.sh`, 25 tests): cover-colour picking, the loudness tone and the blob layout. The tank's logic was split into pure files (`TankPalette.swift`, `LoudnessTone.swift`, `TankBlobs`) so it can be tested without the UI or Core Audio.
- **Automation permission plumbing:** `NSAppleEventsUsageDescription`, the `com.apple.security.automation.apple-events` entitlement (the hardened runtime blocks Apple Events without it), and a footer hint with **Open Automation Settings…** when it's denied.
- **Filter effect.** A high-pass and a low-pass Apple unit in series with one switch. Sliders: **Low cut** 20 Hz–2 kHz and **High cut** 200 Hz–20 kHz, defaults 20 Hz / 20 kHz (no effect). Replaced the removed Compressor and Delay. The high-pass parameter is `kHipassParam_CutoffFrequency` (not `kHighPass…`).
- **10-band Equalizer.** `AVAudioUnitEQ`, ISO centers 31 Hz–16 kHz, parametric bands, 1-octave bandwidth, ±12 dB, matching Apple Music's layout. Gains are stored as one `[Float]`, and each slider gets `eqGainBinding(band:)`. The sliders are vertical, made by rotating a horizontal `Slider`, because SwiftUI has no vertical one.
- **All 22 Apple Music EQ presets** (`EqualizerPresets.all`). Apple has no API for them, so the values are the commonly published iTunes/Music ones and won't sound identical to Music's EQ engine. The selected preset is derived from the gains (`eqPresetName`), not stored, so any slider move shows "Custom" and it can't drift. Picking a preset also turns the EQ on, as Music does.
- **Automatic EQ preamp.** `setEQGains` sets the EQ `globalGain` to minus the combined curve's peak boost (`EqualizerBands.peakBoost`: RBJ peaking-biquad model, 241 log-spaced probe frequencies).
- **Per-effect on/off switches**, separate from the main power switch. The main switch starts and stops the whole capture; the effect switches choose what is applied. Defaults: Reverb on (Hall, 35%), Filter and Equalizer off.
- **`EffectsSettings`.** One struct carries every initial effect value into `TapPipeline.start`, so a rebuilt pipeline starts with current settings.
- **Fixed-size DAW-style layout.** A transport bar, a source panel (left, 220 pt) and an effects rack (right), with always-expanded `EffectModuleBox`es stacked vertically, plus a footer. It keeps the native light look (system colors and materials) instead of a custom dark skin.
- **Helvetica Neue** for titles, section headers and effect names (`Font.display`). Body text stays in the system font, which is more legible at small sizes.
- **`Decisions.md`** (this file).

### Changed
- **Steeper, narrower band filters.** Each band is now two second-order filters in series (24 dB/octave instead of 12), bass below **120 Hz** (was 150) and treble above **7 kHz** (was 5 kHz), so vocals, snares and sibilance leak into the bands much less and the hits that remain are mostly kicks and hi-hats/cymbals.
- **Stronger loudness response in the tank** (user asked for more impact). Sensitivity ±8 dB → ±5 dB from the song's average; brightness range 45–100% → 25–100%; white lift on peaks 15% → 30%; rise 0.3 s → 0.15 s and fall 1.5 s → 0.8 s, so it pulses with the beat. Loudness now also swells the blobs (85%–120% of their size) and their glow (0.7×–1.3× opacity). This reverses the earlier "loudness changes only the tone" decision, which had been chosen to keep the tank calm. All values are constants in `LoudnessTone` and `TankTone`.
- **Apple Music only.** Apple Visualized Music now taps Music and nothing else. Removed the source picker, the **Everything** (system-wide) option, the saved `selectedSource` setting, `TapSpec` (the pipeline takes a process list), the `cannotExcludeSelf` error, and the app name/icon/sort metadata and helpers in `AudioSources.swift`. The 2 s scan stays, but only to track Music's processes and playing state. Reason: the next feature (album-art colours) works through Music's scripting interface, so other apps would have been half-supported. The helper-process mapping in `AudioSources` was kept, since it is the working path for finding Music's audio processes and only Music's own was not checked.
- **Window is 976 × 800 pt: tank on the left, controls on the right.** (680 pt tall until the mini player was added.) The tank was first a 140 pt strip on top (window 560 × 780), then moved to a full-height 400 pt pane on the left to make it bigger, with the controls in a 560 pt column. Side by side keeps the window short and well inside a 1512 × 949 screen. Blob sizes now scale with the tank's area, not its height, so a tall tank doesn't get oversized blobs. Checked by rendering the window to an image.
- **Effects chain** is now source → Equalizer → high-pass → low-pass → reverb → peak limiter → mixer. Tone is shaped first and the room is added last, so the reverb tail is built from the shaped signal. The limiter stays last as a safety net.
- **Effects switch with a bypass**, not by removing nodes (`kAudioUnitProperty_BypassEffect`, `setBypass`). Editing the graph while the engine renders in real time is risky, and this matches the existing "set a property from the work queue" pattern.
- **Effect changes never rebuild the pipeline.** They run on the `AVM.control` work queue so the UI doesn't block on Core Audio.
- **Main window** is a fixed `VStack` instead of a scrolling `Form`, so nothing scrolls except the source list inside its own panel. The footer takes no space once permission is granted and there is no error.
- **Window size is fixed** at 760 × 680 pt (`.frame(width:height:)` plus `.windowResizability(.contentSize)`). At flexible sizes, labels wrapped mid-word. The height grew from 500 to 680 for the Equalizer, and 680 was estimated, not measured.
- **Segmented pickers only for short labels** (Reverb "Space"). Long labels in a 5-segment control overflowed the window.
- **Peak limiter decay set to 60 ms**, the unit's maximum. The 24 ms default is shorter than one cycle of a 31 Hz note (about 32 ms), so the limiter distorted bass when it engaged.
- **Settings are validated on load** (`savedFloat`, `savedBool`, `savedEQGains`, preset whitelists), because a hand-edited preference could otherwise reach an Audio Unit. Imported Objective-C enums accept any raw value.
- **Docs rewritten:** `README.md` and `docs/ARCHITECTURE.md` now describe the current app (effects chain, UI, persistence keys, build details).

### Removed
- **Compressor** (`DynamicsProcessor`) and **Delay** (`AVAudioUnitDelay`). Judged not useful for music streaming. If a compressor is ever re-added, the gain parameter is `kDynamicsProcessorParam_OverallGain`; `MasterGain` is unavailable in Swift.
- **"Murker" lofi block** (`AVAudioUnitDistortion` presets). Apple's distortion presets are overdrive and bit-crush, so they all sounded like a broken speaker. A muffled "next room" sound is a frequency rolloff, which the Filter's **High cut** already does.
- **Waveform visualizer** (ring buffer of per-cycle peaks drawn in a `Canvas`). It didn't animate after two fix attempts (shorter history, square-root curve), and the cause was never found. The menu bar `LevelMeter` is the only level display now. If this is revisited, diagnose why it never moved before changing the visuals.
- **Locked aspect ratio** (`NSWindow.contentAspectRatio` through an `NSViewRepresentable`). A fixed window size made it unnecessary.
- **Dead code**, found by counting references to every declaration: `AVMController.toggle()` (the UI uses `powerBinding`), `ValueSlider`'s `decimals` parameter (only the removed Delay slider used it), and the unused `import AudioUnit` (AudioPipeline) and `import AVFoundation` (Views). Imports that a file uses directly (AppKit, CoreAudio, AudioToolbox) were kept even where another import re-exports them, so builds don't depend on that.

### Fixed
- **No album cover for streamed songs.** Music returns no artwork for many catalogue songs, and the online fallback found nothing, because Apple's search API defaults to the **US store**, where artists like back number aren't listed (2 unrelated results in the US store, the real catalogue in the Thai and Japanese stores). Now the Mac's region's store is searched first, then the US store; an album search is followed by a song search; and a result must match the artist and the album or song title. Taking the first result had picked unrelated releases. Also: a read made mid-change (no song details yet) is retried instead of dropping the cover, and Music's "missing value" artwork is no longer passed to the image decoder. Checked on a real song with no artwork in Music (found in the Thai store) and against the live API. Matching is unit-tested (`CoverSearch.swift`).
- **Shuffle and repeat buttons flickered.** Pressing one updated the button at once, then immediately re-read the setting from Music, which could still report the old value, so the button flipped back until the next reading flipped it again. Now a value set from a button is held for 2 s against re-reads (play/pause too), and shuffle and repeat no longer re-read right after the command, which also halves the main-thread scripts per press. Scripts slower than 100 ms are logged: on the first check only the per-song track read (which includes the cover image) crossed it, at about 120 ms. If button presses still stall the window, the next step is moving scripts off the main thread, which `NSAppleScript` doesn't support, so it would mean sending raw Apple Events.
- **High cut readout was truncated** ("20000…"). Frequencies of 1 kHz and up now read as kHz ("20.0 kHz"). Found in the first window snapshot.
- **Rough sound on boosted EQ presets.** Our chain clips at full scale, but Music's EQ stays in floating point until macOS applies volume, so boosted presets (and overlapping bands) hit the limiter. Fixed by the automatic preamp and the slower limiter decay above. The cost is that boosting presets play a few dB quieter. **Not yet confirmed by ear.**
